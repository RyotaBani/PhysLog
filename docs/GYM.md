# ジム別の器具設定（v1.1）

## 解こうとしている問題

同じ「ベンチプレス 62.5kg」でも、**そのジムで物理的に作れるかどうかが変わります。**

| 課題 | 具体例 |
|------|--------|
| バーの重さが違う | 20kg / 15kg / 10kg |
| プレートの刻みが違う | 1.25kg を置いていないジムがある |
| マシンの重量表記が違う | ポンド表記、独自の段階表記 |
| ダンベルの上限・刻みが違う | 2kg 刻みのジムに 15kg は存在しない |

記録アプリが「どんな数字でも入力できる」ままだと、
**存在しない重量を記録してしまい**、後から見返したときに再現できません。

そこで、ジムごとの器具構成を登録し、**入力候補をそのジムで作れる値に絞ります。**

---

## データ構造

```swift
@Model final class Gym {
    var name: String
    var isDefault: Bool          // 記録画面の既定

    var barWeights: [Double]     // [20, 15, 10]
    var plateWeights: [Double]   // [1.25, 2.5, 5, 10, 15, 20]

    var dumbbellMin: Double
    var dumbbellMax: Double
    var dumbbellStep: Double     // 2kg 刻みなら 15kg は出ない

    var machineUnit: MachineUnit // kg / lb / 段階
    var machineStepWeight: Double?  // 段階表記の1段あたりkg
}
```

### バーベル候補の生成

プレートは左右対称に付けるため、**片側の合計を2倍してバーに足します。**
同じプレートを何枚でも使えるので、無制限ナップサック問題と同じ形です。

検証済みの挙動:

| ジム構成 | 62.5kg | 22.5kg |
|---------|--------|--------|
| 1.25kg プレートあり | 作れる | 作れる |
| 1.25kg プレートなし | **候補に出ない** | **候補に出ない** |

### ポンド換算

内部は kg で統一保存します。表示だけジムの設定に合わせます。

```
1 lb = 0.45359237 kg（国際ヤード・ポンド）

100 lb → 45.4 kg
225 lb → 102.1 kg
```

換算値を保存することで、**ジムを移っても総挙上量が連続します。**
lb のまま保存すると、kg のジムの記録と足し算できなくなります。

### 段階表記

「1番・2番」としか書かれていないマシンがあります。
1段あたりの重量が分からない場合、`machineStepWeight` は nil のままにします。

**このとき総挙上量の計算からは除外します。** 推測値を混ぜると数字が壊れるためです。
段数だけ記録しておき、実測できたら後から換算できます。

---

## 段階的に進める

```
1.1  自分専用のジム登録（端末内・サーバー不要）
1.2  メニューに動画検索リンク、細かい改善
2.0  共有データベース + Pro 課金
```

### なぜ 2.0 を先にやらないか

**共有DBは登録数がゼロだと価値もゼロ**だからです。
「みんなのジム情報」に何も入っていない状態で課金を持ちかけても払われません。

1.1 で自分専用の登録を回してもらい、データ構造を固め、
ユーザーが増えたタイミングで「そのデータを共有できます」と Pro 機能を出す。
この順序なら公開時点で中身が入っています。

### 2.0 の設計方針（UGC 対策）

Apple は ユーザー生成コンテンツを含むアプリに、通報機能・ブロック機能・
24時間以内の対応体制を要求します。個人開発で全国の投稿を毎日監視するのは無理があります。

**回避策は「自由記述をなくす」ことです。**

| 項目 | 入力方式 |
|------|---------|
| バーの重さ | 選択肢のみ |
| プレート | 選択肢のみ |
| ダンベル | 数値のみ |
| マシン表記 | 選択肢のみ |
| **ジム名** | 自由入力だが、**3人以上が同名で登録するまで本人にしか見えない** |

構造化データに悪意は乗りません。誹謗中傷が起こりうるのはジム名だけなので、
そこに昇格制を挟めば審査上の懸念がほぼ消えます。

通報も「情報が違う」の一択で足ります。

## 実装した内容（v1.1）

### ジムの登録

設定 → トレーニング場所 → ジム

- バー・プレートはチェックボックスで選ぶ（実際に置いてあるものだけ）
- 選ぶそばから「作れる重量」がプレビュー表示される
- 「よくある構成」プリセットから選んで、違うところだけ直せる

### 記録するとき

- 既定のジムが自動で入る。毎回選び直す必要はない
- 場所を変えたときだけ切り替える
- 重量欄の下に、そのジムで作れる重量が候補として並ぶ
- **候補はタップで入るが、手入力もそのままできる**

自由入力を残したのは、他店舗で借りた・自前のプレートを使ったといった
例外に対応するためです。候補は入力を速くする補助であって、制約ではありません。

候補は、いま入力されている値に近いものを7件だけ出します。
全部（数十件）出すと、探すほうが手間になるためです。

### 種目の判定

種目名から、バーベル種目かダンベル種目かを推測して候補を切り替えます。

```
「ダンベル」を含む            → ダンベルの重量一覧
ベンチプレス / スクワット など → バーベルの組み合わせ
それ以外                      → 候補を出さない
```

完全な判定は難しいので、外れても自由入力できる前提で作っています。

### 過去の記録との互換

`TrainingSession` は `Gym` への参照ではなく、**ジム名を文字列で持ちます。**
ジムの登録を削除しても、過去の記録が壊れないようにするためです。

ジムを1つも登録していない場合、場所の選択欄そのものが表示されません。
既存ユーザーの記録画面は今までどおりです。

---

## 残りの課題

- 種目判定のキーワードは暫定。使ってみて調整する
- マシン種目の候補は未実装（段階表記の扱いを詰めてから）

# セット単位の記録（v1.2）

## 解こうとしている問題

ウォームアップから本番へ重量を上げていく記録が、打ち直しなしでは作れませんでした。

```
Front Squat  20kg × 10 × 1   ← 種目名から入力し直す
Front Squat  40kg × 5  × 1
Front Squat  60kg × 3  × 1
```

「1つの種目」として見ているのに、行が分かれるのは実態と合いません。

## 構造

`TrainingSet` が `SetEntry` を複数持つ形にしました。

```swift
@Model final class SetEntry {
    var weight: Double?
    var reps: Int?
    var order: Int
}
```

### 旧データとの互換

**旧フィールド（weight / reps / sets）は残しています。**
消すと過去の記録が失われるためです。

`resolvedSets` が両方を吸収します。

| データ | 扱い |
|--------|------|
| `entries` あり | そのまま使う |
| `entries` 空・旧フィールドあり | 同じ内容をセット数ぶん並べたものとみなす |

総挙上量は `Σ(重量 × 回数)` に変わりましたが、
旧形式を展開すると `重量 × 回数 × セット数` と同じ値になります。
**過去のグラフは変わりません。**（検証済み）

### 表示

セットの内容が揃っているかで書き分けます。

```
揃っている → 60kg × 10回 × 3セット
バラバラ   → 20kg×10 / 40kg×5 / 60kg×3
```

繰り返しの多い記録は従来どおり短く、
段階的に上げた記録は内訳が見えます。

## 入力を速くする2つの仕組み

### セットの複製

各セット行の複製ボタンで、同じ内容をもう1本足せます。
「60kg×10 を3セット」なら、1回入力して2回タップで済みます。

### この記録をもとに作成

記録を長押しすると「この記録をもとに作成」が出ます。
種目・セット構成・ジムを引き継いだ状態で新規作成が開くので、
**重量だけ直して保存**できます。

同じメニューを繰り返す日に、種目名から打ち直す必要がなくなります。
